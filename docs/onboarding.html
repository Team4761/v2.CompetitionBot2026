Robockets Programmer Onboarding

Welcome to the team! This guide will walk you through the 2026 competition robot codebase end-to-end — from the folder layout all the way to writing new commands. Everything here is drawn directly from the real source code, so you can trust these examples.

WPILib Command-Based CTRE Phoenix 6 PathPlanner Autos PhotonVision Java 17 Gradle Swerve Drive
💡
New to FRC programming? This guide assumes you know basic Java (classes, methods, inheritance). You don't need to know anything about robots yet — every concept is explained from scratch.

What this guide covers

We have two repos for the 2026 season. v2.CompetitionBot2026 is the active development branch — the code that went to competition. CompetitionBot2026-imported is an earlier version that introduced the turret mechanism. Understanding both will give you the full picture of how the codebase evolved.

The robot uses the Command-Based framework provided by WPILib. The key idea is simple: the robot's hardware is organized into Subsystems, and everything the robot does is expressed as a Command. A Scheduler runs in the background, managing which commands run, and making sure two commands never fight over the same subsystem.

Key rule: subsystems own their commands

Each subsystem folder has a commands/ subfolder. Commands that only affect one subsystem live there. Commands that coordinate multiple subsystems live in the top-level commandGroups/ folder. This keeps things organized as the codebase grows.

⚙️ Subsystems

A Subsystem is a Java class that extends SubsystemBase. It represents a physical piece of the robot — a set of motors, sensors, and state that belong together. The Command Scheduler uses subsystems to prevent conflicts: only one command can control a given subsystem at a time.

Anatomy of a Subsystem

Every subsystem follows the same pattern: declare your hardware as public final fields (so commands can access them directly), configure everything in the constructor, and override periodic() if you need to run code every robot loop (every 20 ms).

KickerSubsystem.java — simplest example
package frc.robot.subsystems.kicker;

import edu.wpi.first.wpilibj2.command.SubsystemBase;
import frc.robot.Constants;
import frc.robot.util.SmartTalonMotor;

public class KickerSubsystem extends SubsystemBase {

    // Hardware declared as public fields so commands can call motor methods
    public final SmartTalonMotor fatKickerInnerMotor;
    public final SmartTalonMotor fatKickerOuterMotor;

    public KickerSubsystem() {
        // Builder pattern — every motor is configured in one fluent chain
        this.fatKickerInnerMotor = SmartTalonMotor.Builder.newInstance()
            .port(Constants.Kicker.FAT_KICKER_INNER_MOTOR_PORT)  // CAN ID 37
            .PID(.1, 0, 0)
            .outputRange(-1, 1)
            .mode(SmartTalonMotor.MotorMode.CONTINUOUS)
            .build();

        this.fatKickerOuterMotor = SmartTalonMotor.Builder.newInstance()
            .port(Constants.Kicker.FAT_KICKER_OUTER_MOTOR_PORT)  // CAN ID 36
            .PID(.1, 0, 0)
            .outputRange(-1, 1)
            .build();
    }
    // No periodic() needed here — commands drive the motors directly
}

A more complex example: ShooterSubsystem

The shooter has four motors: a hood (angle), two spitter wheels (one is a follower), and a backspin wheel. Notice how the second spitter is configured as a Follower — it mirrors the lead motor automatically with no extra code in commands.

ShooterSubsystem.java
public class ShooterSubsystem extends SubsystemBase {

    public final SmartTalonMotor hoodMotor;       // adjusts launch angle
    public final SmartTalonMotor spitterMotor;    // main flywheel (lead)
    public final SmartTalonMotor spitterMotor2;   // second flywheel (follower)
    public final SmartTalonMotor backspinMotor;   // puts backspin on note

    public ShooterSubsystem() {
        this.hoodMotor = SmartTalonMotor.Builder.newInstance()
            .port(Constants.Shooter.HOOD_MOTOR_PORT)              // CAN ID 38
            .PID(1, 0, 0)
            .outputRange(-1, 1)
            .mode(SmartTalonMotor.MotorMode.CONTINUOUS)
            .mechanismAngleLimits(
                Constants.Shooter.Hood.MIN_HOOD_ANGLE_DEGREES,    // 0.0°
                Constants.Shooter.Hood.MAX_HOOD_ANGLE_DEGREES     // 12.5°
            )
            .gearRatio(Constants.Shooter.Hood.MOTOR_ROTATIONS_PER_HOOD_ROTATION) // 325/18
            .build();

        this.spitterMotor = SmartTalonMotor.Builder.newInstance()
            .port(Constants.Shooter.SPITTER_MOTOR_LEAD_PORT)      // CAN ID 31
            .PID(0.1, 0, 0)
            .outputRange(-1, 1)
            .mode(SmartTalonMotor.MotorMode.CONTINUOUS)
            .build();

        this.spitterMotor2 = SmartTalonMotor.Builder.newInstance()
            .port(Constants.Shooter.SPITTER_MOTOR_FOLLOWER_PORT)  // CAN ID 35
            .PID(0.1, 0, 0)
            .outputRange(-1, 1)
            .mode(SmartTalonMotor.MotorMode.CONTINUOUS)
            .build();

        this.backspinMotor = SmartTalonMotor.Builder.newInstance()
            .port(Constants.Shooter.ShootConfig.BACKSPIN_MOTOR_PORT) // CAN ID 34
            .PID(0.1, 0.0, 0.0)
            .outputRange(-1.0, 1.0)
            .mode(SmartTalonMotor.MotorMode.CONTINUOUS)
            .build();

        // Follower: spitterMotor2 mirrors spitterMotor, but spins opposite direction
        this.spitterMotor2.motor.setControl(
            new Follower(
                this.spitterMotor.motor.getDeviceID(),
                MotorAlignmentValue.Opposed   // reversed so both push the note the same way
            )
        );
    }
}

The periodic() method

WPILib calls periodic() on every subsystem exactly once per robot loop (every 20 ms), whether or not a command is running. Use it to publish telemetry, run control loops, or update LED patterns. The LEDSubsystem uses it to animate the bounce pattern:

LEDSubsystem.java — periodic() for animation
@Override
public void periodic() {
    // Rebuild the pattern each loop to advance the animation offset
    LEDPattern rightBase = LEDPattern.steps(Map.of(0, LEDColor1, 0.125, Color.kBlack)).reversed();
    LEDPattern left      = LEDPattern.steps(Map.of(0, LEDColor2, 0.125, Color.kBlack))
                                     .offsetBy((int) LEDOffset);
    LEDPattern right     = rightBase.offsetBy((int) -LEDOffset);

    RobocketsLEDPatterns.bouncePattern = left.overlayOn(right);
    RobocketsLEDPatterns.bouncePattern.applyTo(buffer);
    leds.setData(buffer);

    // Advance the bounce offset each loop
    if (LEDOffset < NUMBER_OF_LEDS - (int)(NUMBER_OF_LEDS * 0.125)) {
        LEDOffset += 0.5;
    } else {
        LEDOffset = 0;
    }
}

▶️ Commands

A Command is a Java class that extends Command. It has four lifecycle methods: initialize() runs once when it starts, execute() runs every loop while it's active, isFinished() tells the scheduler when to stop, and end(boolean interrupted) runs once when it finishes (or is cancelled).

Standard command pattern

The canonical pattern in this codebase: store references to the subsystems you need in the constructor, call addRequirements() so the scheduler knows what you're using, then implement the four lifecycle methods.

FixShootWithPowerCommand.java — a complete, real example
public class FixShootWithPowerCommand extends Command {
    private final ShooterSubsystem shooterSubsystem;
    private final KickerSubsystem  kickerSubsystem;
    private final SliderSubsystem  sliderSubsystem;

    private final DoubleSupplier rpmSupplier;    // live-updated from dashboard
    private final DoubleSupplier angleSupplier;
    private final Timer feederDelayTimer = new Timer();
    private boolean feedersStarted;

    // Convenience overload with fixed values
    public FixShootWithPowerCommand(ShooterSubsystem shooter, SliderSubsystem slider,
                                    KickerSubsystem kicker, double rpm, double angle) {
        this(shooter, slider, kicker, () -> rpm, () -> angle);
    }

    // Primary constructor — accepts suppliers for live dashboard overrides
    public FixShootWithPowerCommand(ShooterSubsystem shooter, SliderSubsystem slider,
                                    KickerSubsystem kicker,
                                    DoubleSupplier rpmSupplier, DoubleSupplier angleSupplier) {
        this.shooterSubsystem = shooter;
        this.sliderSubsystem  = slider;
        this.kickerSubsystem  = kicker;
        this.rpmSupplier      = rpmSupplier;
        this.angleSupplier    = angleSupplier;
        // NOTE: addRequirements() is intentionally omitted here so other commands
        // can run concurrently. Be careful with this pattern!
    }

    @Override
    public void initialize() {
        feedersStarted = false;
        feederDelayTimer.restart();
        // Spin up the flywheel and move the hood immediately
        shooterSubsystem.spitterMotor.setRawSpeed(rpmSupplier.getAsDouble());
        shooterSubsystem.hoodMotor.set(angleSupplier.getAsDouble());
    }

    @Override
    public void execute() {
        // Wait 0.5 s for the flywheel to reach speed, then enable feeders
        if (!feedersStarted && feederDelayTimer.hasElapsed(0.5)) {
            kickerSubsystem.fatKickerInnerMotor.setRawSpeed(-Constants.Kicker.KICKER_SPEED);
            kickerSubsystem.fatKickerOuterMotor.setRawSpeed(-Constants.Kicker.KICKER_SPEED);
            shooterSubsystem.backspinMotor.setRawSpeed(
                -1 * Math.max(0.0, rpmSupplier.getAsDouble() - 2000.0)
            );
            sliderSubsystem.sliderMotor.setRawSpeed(Constants.Slider.SLIDER_RPM);
            feedersStarted = true;
        }
    }

    @Override
    public boolean isFinished() {
        return false;  // runs until the button is released (whileTrue binding)
    }

    @Override
    public void end(boolean interrupted) {
        feederDelayTimer.stop();
        // Always stop all motors on end — even if interrupted
        shooterSubsystem.spitterMotor.stopTurning();
        kickerSubsystem.fatKickerInnerMotor.stopTurning();
        kickerSubsystem.fatKickerOuterMotor.stopTurning();
        shooterSubsystem.backspinMotor.stopTurning();
        sliderSubsystem.sliderMotor.stopTurning();
    }
}

Command Groups

Sometimes you need to coordinate multiple actions. WPILib provides command group classes. These are the ones we use:

Group typeBehaviorWhen to use
SequentialCommandGroupRuns commands one after anotherDo A, then B, then C
ParallelCommandGroupRuns all commands simultaneously; ends when all finishSpin up flywheel AND move hood at the same time
ParallelRaceGroupRuns all simultaneously; ends when the first one finishesDrive forward OR timeout after 3 seconds
ParallelDeadlineGroupRuns all simultaneously; ends when the deadline command finishesRun intake until sensor triggers

Here's ShootWithPowerCommand using nesting to implement the same "delay feeders 0.5 s" pattern declaratively:

ShootWithPowerCommand.java — ParallelCommandGroup example
public class ShootWithPowerCommand extends ParallelCommandGroup {
    public ShootWithPowerCommand(ShooterSubsystem shooter, SliderSubsystem slider,
                                  KickerSubsystem kicker,
                                  DoubleSupplier powerSupplier, DoubleSupplier angleSupplier) {
        super(
            // Branch 1: spin up flywheel + hood immediately
            new SetUpperShooterCommand(shooter,
                -Constants.Shooter.ShootConfig.BACKSPIN_RPM,
                powerSupplier.getAsDouble(),
                angleSupplier.getAsDouble()),

            // Branch 2: wait 0.5 s, THEN run kicker + slider in parallel
            new SequentialCommandGroup(
                new WaitCommand(0.5),
                new ParallelCommandGroup(
                    new KickAtSpeedCommand(kicker, -Constants.Kicker.KICKER_SPEED),
                    new RunSliderAtSpeedCommand(slider, Constants.Slider.SLIDER_RPM)
                )
            )
        );
    }
}

Simple on/off commands

Most subsystem-level commands follow a dead simple pattern. The "on" command spins a motor; the "off" command stops it. Here's the pattern used throughout:

SnatchCommand.java / UnSnatchCommand.java — typical on/off pair
// ON command
public class SnatchCommand extends Command {
    private final SnatcherSubsystem snatcher;
    public SnatchCommand(SnatcherSubsystem snatcher) {
        this.snatcher = snatcher;
        addRequirements(snatcher);
    }
    @Override public void initialize() {
        snatcher.snatcherMotor.setRawSpeedPercent(Constants.Snatcher.SNATCHER_SPEED_PERCENT);
    }
    @Override public boolean isFinished() { return false; }
    @Override public void end(boolean interrupted) {
        snatcher.snatcherMotor.stopTurning();
    }
}

// OFF command — simply stops the motor
public class UnSnatchCommand extends Command {
    private final SnatcherSubsystem snatcher;
    public UnSnatchCommand(SnatcherSubsystem snatcher) {
        this.snatcher = snatcher;
        addRequirements(snatcher);
    }
    @Override public void initialize() {
        snatcher.snatcherMotor.setRawSpeedPercent(-Constants.Snatcher.SNATCHER_SPEED_PERCENT);
    }
    @Override public boolean isFinished() { return false; }
    @Override public void end(boolean interrupted) {
        snatcher.snatcherMotor.stopTurning();
    }
}
✅
Always stop motors in end(). If a command is interrupted (e.g. by another command or by the robot disabling), end(true) is called. If you don't stop motors there, they'll keep spinning indefinitely.

DriveCommand — swerve position control

The DriveCommand shows how to drive the swerve to a relative position using field-centric PID:

DriveCommand.java
public class DriveCommand extends Command {
    private final CommandSwerveDrivetrain drivetrain;
    private final double metersX, metersY, degrees;
    private Pose2d start;
    private PIDController thetaPID;
    private SwerveRequest.FieldCentric drive;

    public DriveCommand(CommandSwerveDrivetrain drivetrain,
                        double metersX, double metersY, double degrees) {
        this.drivetrain = drivetrain;
        this.metersX = metersX; this.metersY = metersY; this.degrees = degrees;
        addRequirements(drivetrain);
    }

    @Override
    public void initialize() {
        start    = drivetrain.getState().Pose;
        thetaPID = new PIDController(Constants.Swerve.Auto.ROTATION_KP, 0, 0);
        drive    = new SwerveRequest.FieldCentric();
    }

    @Override
    public void execute() {
        Pose2d pose = drivetrain.getState().Pose;
        double speedX = (metersX - (pose.getX() - start.getX())) * 2.0;
        double speedY = (metersY - (pose.getY() - start.getY())) * 2.0;
        double omega  = thetaPID.calculate(
            pose.getRotation().getRadians(), Math.toRadians(degrees)
        );
        drivetrain.setControl(
            drive.withVelocityX(speedX)
                 .withVelocityY(speedY)
                 .withRotationalRate(omega)
        );
    }

    @Override
    public boolean isFinished() {
        Pose2d pose = drivetrain.getState().Pose;
        return Math.abs(pose.getX() - start.getX() - metersX) < 0.05
            && Math.abs(pose.getY() - start.getY() - metersY) < 0.05
            && Math.abs(Math.toDegrees(pose.getRotation().getRadians()) - degrees) < 2.0;
    }

    @Override
    public void end(boolean interrupted) {
        drivetrain.applyRequest(() -> new SwerveRequest.Idle());
        thetaPID.close();
    }
}

🎮 RobotContainer

RobotContainer.java is the heart of the robot's wiring. It has three jobs: instantiate all subsystems, bind controller buttons to commands, and register PathPlanner autos. Everything happens in the constructor.

public class RobotContainer {
    // All subsystems are public final fields
    public final SnatcherSubsystem snatcher = new SnatcherSubsystem();

Default drive command

The swerve drivetrain's default command is the field-centric drive. It reads from the left joystick (translation) and right joystick (rotation) every loop. The SlewRateLimiter smooths rotation acceleration so the robot doesn't snap:

RobotContainer.java — configureDefaultDrive()
private void configureDefaultDrive() {
    drivetrain.setDefaultCommand(
        drivetrain.applyRequest(() -> {
            double xInput = -1 * applyDeadband(
                controller_drive.getLeftY(),
                Constants.Controller.TRANSLATION_INPUT_DEADBAND   // 10%
            );
            double yInput = -1 * applyDeadband(
                controller_drive.getLeftX(),
                Constants.Controller.TRANSLATION_INPUT_DEADBAND
            );
            double turnInput = shapeTurnInput(
                -1 * applyDeadband(
                    controller_drive.getRightX(),
                    Constants.Controller.ROTATION_INPUT_DEADBAND  // 12%
                )
            );
            return drive
                .withVelocityX(xInput * MaxSpeed)
                .withVelocityY(yInput * MaxSpeed)
                .withRotationalRate(
                    rotationLimiter.calculate(
                        turnInput * Constants.Controller.ROTATION_MULTIPLIER * MaxAngularRate
                    )
                );
        })
    );
}

Controller bindings

WPILib's CommandXboxController exposes every button as a Trigger object. You attach commands using .whileTrue() (runs while held), .onTrue() (runs once on press), or .toggleOnTrue().

RobotContainer.java — driver and operator bindings
private void configureDriverBindings() {
    // Back button: reset field-centric heading (useful after robot rotates)
    controller_drive.back().onTrue(drivetrain.runOnce(drivetrain::seedFieldCentric));

    // Right bumper: extend intake arm (runs once and holds position)
    controller_drive.rightBumper().onTrue(new SmackdownSnatcherCommand(snatcher));
    // Left bumper: jostle stuck game piece
    controller_drive.leftBumper().onTrue(new JostleSnatcherCommand(snatcher));

    // Triggers: intake / outtake (hold to run, release to stop)
    controller_drive.rightTrigger().whileTrue(new SnatchCommand(snatcher));
    controller_drive.leftTrigger().whileTrue(new UnSnatchCommand(snatcher));

    // Operator A: auto-orient robot toward hub
    controller_operator.a().whileTrue(new AutoOrientCommand(drivetrain));
}

private void configureOperatorBindings() {
    // Right trigger: live-tunable shoot (RPM from Elastic dashboard slider)
    controller_operator.rightTrigger().whileTrue(
        new FixShootWithPowerCommand(
            shooter, slider, kicker,
            () -> MathUtil.clamp(
                SmartDashboard.getNumber(
                    Constants.Dashboard.ELASTIC_TEST_SHOOTER_RPM,
                    Constants.Shooter.ShootConfig.MEDIUM_SPITTER_SPEED
                ),
                Constants.Dashboard.ELASTIC_TEST_SHOOTER_RPM_MIN,   // 3000 RPM
                Constants.Dashboard.ELASTIC_TEST_SHOOTER_RPM_MAX    // 6500 RPM
            ),
            () -> 0.0
        )
    );

    // Y/X/A: three preset shooting distances
    controller_operator.y().whileTrue(new ShootWithPowerCommand(shooter, slider, kicker, () -> 10000, () -> 12.5)); // long
    controller_operator.x().whileTrue(new ShootWithPowerCommand(shooter, slider, kicker, () -> 7000,  () -> 10.0)); // medium
    controller_operator.a().whileTrue(new ShootWithPowerCommand(shooter, slider, kicker, () -> 5000,  () -> 5.0));  // short

    // Manual overrides: hold left trigger + button to isolate individual motors
    controller_operator.leftTrigger().and(controller_operator.a())
        .whileTrue(new SpinSliderCommand(slider));
    controller_operator.leftTrigger().and(controller_operator.x())
        .whileTrue(new RunSpitterCommand(shooter, Constants.Shooter.ShootConfig.MEDIUM_SPITTER_SPEED));
    controller_operator.leftTrigger().and(controller_operator.rightBumper())
        .whileTrue(new KickCommand(kicker));
}
💡
The .and() trick: controller_operator.leftTrigger().and(controller_operator.a()) creates a Trigger that only fires when both are held. This is how manual override mode works — hold LT as a "shift key", then press other buttons for individual motor control.

Robot.java — match lifecycle

Robot.java extends TimedRobot and hooks into the match phases. The most important thing here is that robotPeriodic() runs the CommandScheduler — this is what actually executes your commands every loop:

Robot.java — key lifecycle methods
@Override
public void robotPeriodic() {
    m_timeAndJoystickReplay.update();   // log joystick data for replay
    CommandScheduler.getInstance().run(); // ← THIS runs all commands
    updateDashboard();                    // push telemetry values to SmartDashboard
}

@Override
public void autonomousInit() {
    Constants.Field.STARTING_POSITION = positionChooser.getSelected(); // LEFT/CENTER/RIGHT
    m_autonomousCommand = robotContainer.getAutonomousCommand();
    if (m_autonomousCommand != null) {
        CommandScheduler.getInstance().schedule(m_autonomousCommand);
    }
    matchTimer.reset(); matchTimer.start();
}

@Override
public void teleopInit() {
    // Cancel auto command when teleop starts
    if (m_autonomousCommand != null) {
        m_autonomousCommand.cancel();
        m_autonomousCommand = null;
    }
}

Robot.java also tracks match phase with a simple enum (AUTONOMOUS → TRANSITION → TELEOP_FIRST_SHIFT → ... → ENDGAME) using timer-based transitions in teleopPeriodic(). This allows LED patterns and other behaviors to change as the match progresses.

🔧 Motors

All motors on this robot are CTRE TalonFX (brand name: Kraken X60 or Falcon 500). We don't call the TalonFX API directly — instead we use a custom wrapper class, SmartTalonMotor, that hides boilerplate and adds safety features.

SmartTalonMotor — the wrapper

The wrapper provides three things: a Builder pattern for clean configuration, automatic gear ratio conversion (so you always work in mechanism units, not motor rotations), and enforced angle limits that log warnings and reject out-of-range commands instead of crashing.

Gear ratio in practice

The hood motor has a 325:18 gear ratio (motor spins ~18x faster than the hood). When you configure .gearRatio(325.0/18.0), calling hoodMotor.set(10.0) moves the hood to 10 degrees — the wrapper calculates the motor rotations automatically. You never have to think about the gearbox.

Inside SmartTalonMotor — gear ratio conversion
// Convert mechanism degrees → motor rotations for the TalonFX position controller
private double toMotorRotations(double mechDegrees) {
    return (mechDegrees / 360.0) * this.gearRatio;
}

// Convert motor rotations → mechanism degrees for reading back position
private double toMechanismDegrees(double motorRotations) {
    return (motorRotations * 360.0) / this.gearRatio;
}

// set() enforces angle limits before sending any motor command
public boolean set(double mechDegrees) {
    if (isWithinLimits(mechDegrees)) {
        motor.setControl(positionRequest.withPosition(toMotorRotations(mechDegrees)));
        return true;
    }
    LOGGER.warning(String.format(
        "[set] Rejected angle %.2f°; limits are [%.2f°, %.2f°]",
        mechDegrees, minAngleDeg, maxAngleDeg
    ));
    return false;   // returns false so callers can react if needed
}

Two motor modes

MotorMode.CONTINUOUS is for mechanisms that have hard stops (like a hood that swings 0–12.5°). Limits are enforced and the motor holds position. MotorMode.WRAPPED is for spinning mechanisms (like a kicker wheel) where any angle is valid and position wraps at 360°.

📷 Vision

We use PhotonVision running on a coprocessor (Raspberry Pi or Orange Pi) to detect AprilTag fiducial markers around the field and feed pose estimates into the drivetrain's odometry. Two cameras are mounted on the back of the robot, pointed outward.

How it works

  1. PhotonVision runs on the coprocessor and publishes AprilTag detection results over NetworkTables.
  2. VisionSubsystem.periodic() reads new results from both cameras every loop.
  3. Each result is filtered: single-tag results must have low ambiguity (< 0.20) and be within 4 meters. Multi-tag results pass with looser constraints.
  4. Accepted results are fed to drivetrain.addVisionMeasurement() with a standard-deviation matrix that encodes our confidence in the measurement (farther away = less confident).
  5. The drivetrain's pose estimator fuses these vision updates with wheel odometry using a Kalman filter.
VisionSubsystem.java — periodic() filtering logic
@Override
public void periodic() {
    currentPose = drivetrain.getState().Pose;

    if (!enabled) return;

    Pose3d referencePose = new Pose3d(currentPose);

    for (CameraContext cameraContext : cameras) {
        for (PhotonPipelineResult result : cameraContext.camera.getAllUnreadResults()) {

            if (!result.hasTargets()) {
                recordRejectedMeasurement(cameraContext.config.name(), "No targets");
                continue;
            }

            // Single-tag results: check pose ambiguity
            if (result.getTargets().size() == 1) {
                double ambiguity = result.getBestTarget().getPoseAmbiguity();
                if (ambiguity < 0.0 || ambiguity >= SINGLE_TAG_AMBIGUITY_CUTOFF) { // 0.20
                    recordRejectedMeasurement(cameraContext.config.name(), "High ambiguity");
                    continue;
                }
            }

            // Try multi-tag pose first (more accurate), fall back to closest-to-reference
            Optional<EstimatedRobotPose> estimate =
                cameraContext.poseEstimator.estimateCoprocMultiTagPose(result);
            if (estimate.isEmpty()) {
                estimate = cameraContext.poseEstimator.estimateClosestToReferencePose(
                    result, referencePose
                );
            }

            if (estimate.isEmpty()) {
                recordRejectedMeasurement(cameraContext.config.name(), "No estimate");
                continue;
            }

            // Check distance for single-tag results
            double distanceToNearestTag = calculateDistanceToNearestTag(estimate.get());
            if (result.getTargets().size() == 1
                    && distanceToNearestTag > MAX_SINGLE_TAG_DISTANCE_METERS) { // 4.0m
                recordRejectedMeasurement(cameraContext.config.name(), "Too far");
                continue;
            }

            // Assign standard deviations based on tag count
            Matrix<N3, N1> stdDevs = result.getTargets().size() > 1
                ? MULTI_TAG_STD_DEVS   // [0.35, 0.35, 0.75]  — high confidence
                : SINGLE_TAG_STD_DEVS; // [1.5, 1.5, 6.0]     — lower confidence

            // Feed accepted measurement to drivetrain Kalman filter
            drivetrain.addVisionMeasurement(
                estimate.get().estimatedPose.toPose2d(),
                estimate.get().timestampSeconds,
                stdDevs
            );
        }
    }
}

🤖 Autonomous Routines

Autonomous routines are built with PathPlanner. You design paths visually in the PathPlanner GUI app and the robot follows them using the built-in path-following controller. Commands (like "shoot while driving") are triggered from within paths as named commands.

How PathPlanner is wired in

Before any auto runs, we register named commands — these are the Java commands PathPlanner can call by name from within a path. This registration happens in RobotContainer.configurePathPlannerAutos():

RobotContainer.java — named command registration
private void configurePathPlannerAutos() {
    drivetrain.initializeAutoBuilder();  // must happen before buildAutoChooser()

    // Register every command PathPlanner paths can reference by name
    NamedCommands.registerCommand("DoNothingCommand",
        Commands.none());
    NamedCommands.registerCommand("AutoShootCommand",
        new AutoShootCommand(drivetrain, shooter, slider, kicker));
    NamedCommands.registerCommand("SnatchCommand",
        new SnatchCommand(snatcher));
    NamedCommands.registerCommand("UnSnatchCommand",
        new UnSnatchCommand(snatcher));
    NamedCommands.registerCommand("SmackdownSnatcherCommand",
        new SmackdownSnatcherCommand(snatcher));
    NamedCommands.registerCommand("Shoot Long",
        new FixShootWithPowerCommand(shooter, slider, kicker,
            () -> Constants.Shooter.ShootConfig.LONG_SHOOT_RPM, () -> 10.0));
    NamedCommands.registerCommand("Shoot Medium",
        new FixShootWithPowerCommand(shooter, slider, kicker,
            () -> Constants.Shooter.ShootConfig.MEDIUM_SHOOT_RPM, () -> 12.5));
    NamedCommands.registerCommand("Shoot Short",
        new FixShootWithPowerCommand(shooter, slider, kicker,
            () -> 5000.0, () -> 10.0));

    // Build auto chooser and populate it from PathPlanner auto files on the roboRIO
    autoChooser.setDefaultOption("None", Commands.none());
    for (String autoName : AutoBuilder.getAllAutoNames()) {
        try {
            if (!autoName.startsWith("UNM")) {
                // Most autos can be run from either side — add LEFT and RIGHT variants
                autoChooser.addOption("LEFT "  + autoName, new PathPlannerAuto(autoName, false));
                autoChooser.addOption("RIGHT " + autoName, new PathPlannerAuto(autoName, true));
            } else {
                // UNM- prefixed autos are symmetric (e.g. center starts)
                autoChooser.addOption(autoName, new PathPlannerAuto(autoName));
            }
        } catch (Exception e) {
            DriverStation.reportError("Skipping invalid auto '" + autoName + "': " + e.getMessage(),
                e.getStackTrace());
        }
    }
    SmartDashboard.putData("PathPlanner Auto Chooser", autoChooser);
}

Adding a new auto

  1. Open the PathPlanner app. Create a new auto and design your path(s). Drag named command events onto the path where you want them to fire.
  2. Export the .auto and any new .path files to src/main/deploy/pathplanner/.
  3. If your auto calls new commands, register them with NamedCommands.registerCommand("MyCommandName", new MyCommand(...)) in configurePathPlannerAutos().
  4. Deploy to the roboRIO. The new auto will automatically appear in the SmartDashboard/Elastic chooser.
💡
LEFT/RIGHT mirroring: Autos without the UNM- prefix are automatically mirrored for the other side of the field. PathPlanner handles the coordinate flip. This means you only need to design each auto for one side.

The CommandSwerveDrivetrain calls AutoBuilder.configure() in its constructor (via initializeAutoBuilder()), providing the pose supplier, pose resetter, chassis speed supplier and consumer, plus the drive robot controller. You don't need to touch this — it's set up in the generated file.

File organization

Each subsystem lives in its own package under subsystems/ — for example, subsystems.kicker. The subsystem class and all commands that only affect that subsystem go in the same package. Multi-subsystem commands go in commandGroups/. Hardware wrappers (SmartTalonMotor etc.) go in util/.

Patterns that repeat everywhere

Builder pattern for configuration

All motor setup uses the Builder pattern. Never pass a raw TalonFX around — always wrap it in SmartTalonMotor. This makes configuration readable and keeps the constructor clean.

DoubleSupplier for live values

When a command needs a value that might change during execution (like an RPM being tuned from the dashboard), we pass a DoubleSupplier (a lambda () -> value) instead of a plain double. The supplier is evaluated fresh every call.

Supplier example — live dashboard value
// Bad: value is frozen at command creation time
new FixShootWithPowerCommand(shooter, slider, kicker, 5000.0, 10.0);

// Good: lambda re-reads the dashboard every execute() tick
new FixShootWithPowerCommand(shooter, slider, kicker,
    () -> SmartDashboard.getNumber("Elastic Test Shooter RPM", 5000.0),
    () -> 0.0
);

Always call addRequirements()

In any command that directly controls motors, call addRequirements(subsystem) in the constructor. This prevents two commands from fighting over the same motor. The only exception is intentional concurrent control (rare — see FixShootWithPowerCommand which deliberately omits it to allow simultaneous drive).

stopTurning() in end()

Every command that starts a motor must stop it in end(). Pass-through to SmartTalonMotor.stopTurning() — never call raw TalonFX methods in commands.

Constants, not magic numbers

Zero raw numbers in command or subsystem code. Every port, speed, angle, and threshold goes through Constants. If you find yourself writing a literal number anywhere outside Constants.java, stop and add a constant instead.

✨ Adding New Code

Adding a new subsystem

  1. Create a new package: src/main/java/frc/robot/subsystems/mysubsystem/
  2. Create MySubsystem.java extending SubsystemBase. Declare motors as public final SmartTalonMotor fields. Configure them in the constructor using the Builder pattern. Add CAN IDs to Constants.java first.
  3. Create a commands/ subfolder and add your commands there.
  4. In RobotContainer.java, add public final MySubsystem mySubsystem = new MySubsystem(); as a field.
  5. Wire buttons to commands in configureDriverBindings() or configureOperatorBindings().

Adding a new command

  1. Create MyActionCommand.java in the appropriate commands/ folder.
  2. Extend Command. Store subsystem references in final fields. Call addRequirements(subsystem) in the constructor.
  3. Implement initialize(), execute(), isFinished(), and end(boolean). At minimum, always implement end() to stop motors.
  4. Use it in RobotContainer or register it with NamedCommands for PathPlanner.

Adding a new constant

  1. Open Constants.java. Find the right inner class (e.g. Constants.Shooter.ShootConfig for a shooting speed).
  2. Add public static final double MY_NEW_CONSTANT = 1234.0;.
  3. Reference it as Constants.Shooter.ShootConfig.MY_NEW_CONSTANT in your command or subsystem.

Adding a new PathPlanner auto

  1. Design the path in the PathPlanner app. Add named command events where needed.
  2. Export to src/main/deploy/pathplanner/.
  3. If the auto uses new commands, register them in configurePathPlannerAutos() with NamedCommands.registerCommand("Name", new MyCommand(...)).
  4. Deploy. The auto appears automatically in the dashboard chooser.
🚨
Before your first deploy, double-check: (1) CAN IDs in Constants match the physical hardware, (2) motor directions are correct (a reversed motor can damage mechanisms), (3) soft limits are set and tested on a benched robot before running on the field.
